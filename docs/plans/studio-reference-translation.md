# Studio 下一阶段提案：Agent 看图驱动的角色临摹

日期：2026-09-30。状态：方向已确认，首步工具原型按 ADR-0014 实施；后续阶段仍为提案。
实际使用合同见 `../studio-raster.md`，验证边界见 `../verification.md` 的 S11。
首版采用有界内嵌像素，而非下述远期外部资源仓库；不把本提案的全部能力列为已交付。
2026-10-01：ADR-0015 已补显式等比例最近邻尺寸草稿及点位联动；T1 的完整视觉验收与另一种角色仍未完成。

用户已明确：允许生成或导入位图；制作不必完全在 Studio 内完成。
Agent 可以通过 Studio 创建和修改，再用自己的看图能力检视和决定下一步。
本提案不要求把人物重新拆成现有 humanoid 配方，也不把外部图像生成器设为必需前置。

## 1. 建议方向

把 Studio 从“程序化资产的受控编辑层”扩展为“视觉 agent 可直接使用的游戏资产创作工具”。
目标是让 agent 保留用户指定的角色身份，按游戏的尺寸、画风、比例和使用条件重新表现，
并交付可以继续修改、能在游戏里正确显示的资产。

这里的“临摹”包括设计保真和受控改编，不等于逐像素复制，也不等于生成一个相似题材的新角色。
例如用户允许改成 Q 版，就可以改变头身比；未允许更换的发型、服饰结构和标志物仍须保留。

**Agent 看图、判断和安排修改；Studio 负责创建、绘改、渲染、回退和技术检查。**
Studio 不必自己理解角色，也不只负责生成后的格式整理。
日常视觉检查默认由当前 agent 自己完成；人工确认和独立评审不是每轮制作的必经步骤。
Studio 不在纯核心里调用视觉模型，也不把技术 PASS 当成角色还原成功。

建议先做一个垂直闭环，而不是先建设完整绘图软件、通用角色模型或模型服务平台。

## 2. 依据与现状

实施者必须以 [CONTEXT.md](../../CONTEXT.md) 为术语和模块边界来源，以
[docs/adr/](../adr/) 为架构决策来源；当前没有 CONTEXT-MAP.md，建立后按其定位子域。
现行范围见 [PLAN.md](../PLAN.md)，证据与限制见 [verification.md](../verification.md)。

本提案重点沿用 ADR-0001 的核心与 IO 分层、ADR-0002 的坐标合同、ADR-0004 的共享烘焙、
ADR-0005 的轻量 Canvas 边界、ADR-0008/0009 的文档和事务，以及 ADR-0012/0013 的最终结果复验原则。
ADR-0010/0011 的风格与角色能力继续保留，但不能据此宣称已有通用角色临摹能力。

| 已有事实 | 对新方向的意义 |
|---|---|
| `src/export/png.js` 已有 PNG 编解码；`PixelPainter.fromRGBA` 可接收像素 | 不必重写 PNG 与像素缓冲基础设施，但还没有完整的 Studio 位图编辑工作流 |
| `assembleFrame`、`assembleAsset`、CanvasBank 与图集导出已有共用路径 | 新来源最终仍产出标准帧，不另建游戏消费格式 |
| 工作区已有候选、修订、保护、提交重验和恢复 | 可复用事务原则；外部位图资源的存储、解析和身份绑定仍需扩展 |
| `character/1` 只支持一个 humanoid 模板；头和躯干 ASCII 部件限 16×16，内画布边长限 64 | 不适合作为任意人物设计、服装和体型的唯一表达方式 |
| humanoid 四肢、鞋和枪存在固定绘制规则 | 继续堆模板参数不能替代自由造型，尤其是长衣、复杂头饰和非模板比例 |
| `PixelPainter.blit` 不做半透明混合；帧组装默认加描边和扩边 | 位图接入必须明确 alpha、描边与最终尺寸，不能默认“导入即可兼容” |
| v1.4 开发交付尚未独立认证；既往实验没有证明 Studio 的普遍 agent 优势 | 不把旧约束实验当成临摹效果证据，也不为本提案重跑旧实验 |

本节是提出方向时的现状检查；后续实现与样图验证单独记录在 verification.md，不追改历史实验结论。

## 3. 用户体验与生产流程

```text
角色设计图 + 可选风格图 + 游戏规格
  → agent 自己看图，确定必须保留的设计与允许变化
  → 创建初稿：Studio 直接绘制 / 现有配方 / 导入位图 / 外部生成
  → Studio 渲染目标尺寸与局部观察图
  → agent 实际看图，对照参考指出具体差距
  → 用 Studio 绘改，必要时调用外部工具后再导入
  → 重新渲染和看图；改善则接受，退步则恢复，直至达标或报告限制
  → 技术检查与游戏预览 → 标准帧、Canvas 接入或图集导出
```

任务说明保持简短，记录目标和少数关键设计特征即可，不先建设庞大的角色语义数据库。
用户只需处理会影响身份的歧义或自行选择最终效果；要求已经明确时 agent 直接制作。
每轮观察都绑定实际候选和图像；返回 PNG 路径或模型自述“已检查”不能替代图像输入。

示例任务：用户提供带角状头饰、红围巾和长靴的人物，要求最终 48×64 像素单元、
透明背景、指定像素画风、保留服装结构，可以适当夸张头部比例。
首轮先检查头饰轮廓、围巾色块和长靴是否在实际显示尺寸可辨；
Agent 发现头饰外缘不对，就用 Studio 调轮廓、补色块或替换局部，再自己看新图。
修改不必经过整图再生成，也不要求所有局部都能被语义识别器自动命名。
本例只说明流程，不规定后续角色必须具有这些特征。

## 4. 必须分开的三类约定

### 4.1 设计保真

- 参考图记录明确用途：`identity`（角色设计）、`style`（画风）、`pose`（姿态）或 `quality`（质量标杆）。同一图可有多个显式用途。
- Agent 提取轮廓、体型、发型、服装层次、关键配色关系、非对称标记和标志物。
- 每项使用稳定 feature ID，关联来源图 ID 与必要的区域坐标；区分用户指定、图中可见、agent 推测。
- 区分必须保留、允许概括、允许改编、尚不明确。不可见的背面、被遮挡的配件不冒充已知事实。
- 指定用途间有冲突时解释取舍；例如换配色风格不能自动覆盖用户要求保留的红围巾。
- 文字约定参与任务版本与评审身份绑定，但机器只能校验记录完整，不能证明视觉特征已正确还原。

当前普通技能和 ADR-0007 的默认方向是“质量同级、允许原创”。新增显式的
`reference-translation` 工作流：用户角色设计要保真，画风参考不自动带入其中的人物身份。
普通原创工作流与 `pga-loop/2` 不改默认含义；不在本阶段迁移循环合同或引入双批次准出。

### 4.2 风格与造型转换

风格不能只写“像素风”或“换调色板”。至少说明轮廓线、色阶、明暗组织、像素块尺度、
抗锯齿/抖色策略，以及哪些细节可以合并。头身比属于造型授权，不能由画风切换暗中改变。

每个目标尺寸独立审图。高分辨率图降采样可以得到草稿，但不能直接宣布临摹完成。
在小尺寸里可以把装饰概括成几块像素；如果必须保留的细节已无法辨识，
应报告尺寸与设计要求冲突，选择更大尺寸或经用户同意简化，不静默删除。

首阶段只正式支持一种约定清楚的像素风输出；平滑插画、复杂半透明与多画风转换后置。
可以导入其他画风的设计原图，但这不代表首阶段可输出任意画风。

### 4.3 游戏规格

明确最终帧尺寸、角色像素高度、留白、视角、朝向、实际显示倍率、alpha 规则、
脚底锚点、需要的附件点和背景条件。三个尺寸概念分别记录：源图尺寸、最终帧尺寸、游戏显示尺寸。

最终尺寸必须包含留白和描边。不能先得到 48×64，再由默认组装步骤变成 50×66。
已有描边的位图不自动二次描边；裁切、缩放、扩边都必须同步变换锚点和附件点。
像素边界坐标继续使用 ADR-0002，不引入另一套运行时坐标。

镜像不是免费增加一个正确视角：非对称徽记、手持物和文字可能需要独立修整。
新视角和新动作属于新的制作范围，不能从单张设计图宣称已经验证。

## 5. Studio 要新增的最小能力

| 能力 | 首阶段做到什么 | 不在首阶段做什么 |
|---|---|---|
| 参考材料与任务说明 | 保存原图、用途、设计要点与目标规格，均有稳定 ID 和版本 | 自动理解所有人物结构、自动补全未知视角 |
| 直接创建与绘改 | 创建透明画布，有限批量像素/线条/多边形绘制、区域填色与擦除；复用既有绘制原语 | 让 agent 每次另写绘图程序，或只能导入而不能直接画 |
| 位图文档 | 单帧基础位图、显式编辑记录、锚点、有限区域掩码 | 任意混合模式、完整图层面板、PSD 兼容 |
| 目标尺寸修整 | 显式裁切/定位/尺寸适配、有限调色板映射和 alpha 清理，并产出候选 | 把一次缩图或量化当成风格转换成功 |
| 局部修改 | 按预先声明的掩码替换候选像素，支持透明擦除，保护区域外像素 | 仅凭生成提示词保证“不改其它地方” |
| 对比观察 | 原图与候选独立展示、原尺寸/放大/剪影/明暗背景视图、修改前后差分 | 用单一图像相似度分数自动放行 |
| 游戏交付 | 标准帧、锚点和必要附件点、Canvas 场景预览、现有导出格式 | 自动生成碰撞玩法或通用引擎适配 |

优先补“创建初稿 → 看图 → 局部修正”的完整操作面，而不是只补导入或导出。
绘制操作支持有限批量，一次修改一个可观察的意图，不要求 agent 为每个像素调用一次工具。
选区使用明确的 rect/poly/mask 和稳定 region ID；支持查看选区覆盖，避免只凭坐标猜测。

“局部替换”也是首阶段能力。外部模型即使把整张候选都改了，Studio 也只取允许区域，
其余像素从确认过的基准保留。替换包含 RGBA 四通道，alpha=0 能擦除；
不能直接用会跳过透明像素的 `blit` 来假装实现擦除。
区域外不变可以由机器保证；区域接缝、遮挡关系和角色相似度仍需看图。

处理不干净的背景时不默认按白色删除，否则会破坏衣服、眼白和高光。
掩码与去背结果也进入候选，必须在明暗背景检查；不把画出来的棋盘格当成真透明。

## 6. 架构建议与兼容边界

### 6.1 Agent 主导，外部生成可选

Agent 可以从透明画布直接绘制，也可以沿用程序化配方、导入位图或调用宿主图像能力得到初稿。
选哪条路径取决于目标和工具能力，不设强制的“先整图生成、再进 Studio”。
首版不内置账号、模型路由、云端队列或强制的服务商 SDK；没有生成能力也能创建和修改。
需要时记录来源、提示词、可获得的模型信息与结果哈希，不记录密钥，不补造服务端未暴露的参数。

外部生成本身可能不可复现；将生成结果冻结为输入后，Studio 内的编辑、编译与导出可以重放。
恢复修订不重新调用模型。模型输出未经验收，不自动成为已确认资产。

### 6.2 新位图文档，不扩充旧 humanoid 模板冒充自由造型

首步已新增独立文档族 `pga-studio/raster/1`，在 `src/studio/dispatch.js` 显式分派。
实际字段以 ADR-0014 和 `studio-raster.md` 为准；未知版本拒绝，不能落入 prop 分支。

首版像素内嵌在有界 JSON 文档中。以下外部资源仓库和任务版本合同属于后续建议，尚未实施：

编辑文档记录透明画布或基础像素资源、版本化绘制/编辑操作、掩码、规格和元数据。
大图和原始参考文件由 IO 层管理为内容寻址的不可变资源；文档只使用资源 ID/哈希，
不携带可执行内容、任意模块路径或网络 URL。纯编译函数接收显式解析好的像素数据。

这会改变现有“修订只存 JSON 即足够”的假设。新增资源须先完整落盘并校验，最后才更新 head；
资源缺失或哈希不符必须失败。候选、提交、恢复与导出均核对资源身份，不能只核对文档 JSON。
首版不做自动资源回收，避免删除旧修订需要的像素；记录资源数量和大小上限。
可携带编辑包包含文档及重放所需资源，不能依赖当前机器的隐式缓存；参考材料的携带范围单独声明。

冻结任务说明和候选绑定参考、规格、文档、掩码、像素资源、工具版本。
改变目标尺寸、保真要求或允许修改区域，需要显式产生新任务版本，并使旧评审失效；
编辑操作不能暗中放宽合同，restore 也不能解除当前合同。

### 6.3 继续共享帧与交付路径

```text
Agent 指令：空白创建 / 配方初稿 / 导入已有或生成的位图
  → IO 适配：按需解码、资源检查与存储；不参与视觉判断
  → Studio：文档 + 纯绘制/编辑操作 + 最终保护检查
  → 既有帧组装 / BakedAsset
  → 共享观察图 → agent 自己看图 → 下一轮编辑或交付
  → CanvasBank 或 PNG 图集 / manifest
```

文件解码和资源读取留在 adapters/IO，核心不读文件、不联网。
来源与编辑历史不塞进游戏 manifest；manifest 的兼容性、asset kind 和当前验证器约束需在实施时一起核对，
不为绕过校验把任意位图伪装成现有 humanoid 或 prop。

首阶段正式产物采用明确的像素风 alpha 约定，建议为 0/255；带半透明的原图保留，
转为二值 alpha 必须显式预览和接受。平滑 RGBA 输出以后再扩展，不能沿用“不做混合”的 blit 宣称已支持。
解码后统一朝向、颜色解释和 straight RGBA 约定，再计算规范化像素哈希；
最初可只收 PNG，其他格式由明确的转换入口处理，不静默忽略颜色或朝向信息。

Studio 的位图操作和角色配方并存。程序化路径仍适合批量变体、地形与规则性配件，
不再要求所有用户角色都能被同一套几何参数表达。

## 7. “可靠”的验收定义

分别记录四个结论，不用一个总分互相抵消：

| 维度 | 判定方式 | 不能替代它的证据 |
|---|---|---|
| 设计保真 | Agent 实际对照参考检查必须保留的特征与允许变形，记录具体差距 | 提示词写过、feature 字段存在、图像整体相似度高 |
| 目标风格 | 目标尺寸下看轮廓、色块、细节密度和一致性 | 只看大图、只做换色、只满足颜色数 |
| 技术可用 | 尺寸/alpha/边界/坐标/图集往返/资源重放/局部保护自动检查 | 图看起来正常或生成器自报规格 |
| 游戏可读 | 在声明背景和显示倍率下真实预览；动画阶段实际播放 | 透明棋盘背景截图或动画 contact sheet |

机器硬检查失败不得通过交付。视觉未检查记 `UNVERIFIED`，有明确缺陷记 `NOT_YET`；
只有四项在声明范围内成立才称“可用资产”。可以保存草稿，但草稿导出不等于验收完成。
图像相似度、颜色比例、连通区域等可以提示问题，不负责最终审美或身份裁决。
当前 agent 的视觉检查如实标为自检，不冒充独立验证。只有用户要求严格认证或做正式比较实验时，
再采用独立评审；不把 asset-loop 的长循环规则默认施加到本工作流。
明确候选/成本上限和停滞条件；若连续修改没有解决同一差距，报告工具缺口或规格冲突，
不靠无限重试声称可靠。具体预算随任务约定，不在本提案凭空固定成功率。

评审材料用 Reference R、Candidate X/Y、Feature F 等稳定符号标识；
contact sheet 标签在资产像素外，交换排布不改变身份。不用画面位置当候选名称。
视觉结论绑定具体版本；重采样、改色、局部修复后按影响范围重新检查，不能沿用失效结论。

## 8. 建设顺序

### T0：参考设计到单帧资产的完整闭环

先做一张人物设计、同一已知视角、一种明确像素画风、一个目标帧尺寸。
第一张样图就走“agent 看参考 → 创建初稿 → 看输出 → 具体修改 → 再看 → 游戏预览”。
初稿来源不限，但必须真实使用 Studio 创建/编辑能力，不能只拿预制精灵证明导入器可用。

最低能力：简短临摹说明、画布创建、有限绘改、基础位图导入、掩码替换、候选/恢复、对比视图和标准帧交付。
用一次来自 agent 实际看图的局部修复验证“识别差距 → 改对目标 → 不改坏其余区域”。
通过条件：角色关键特征获视觉确认，最终尺寸和透明度正确，Canvas 真实显示，
PNG/manifest 往返一致，从编辑包重开并重放成功，保护区域外像素逐字节不变。

这一步的可复用收益是确认 agent 能否把看图发现的差距转成 Studio 操作，以及位图是否适配现有事务链。
不把打磨一张演示图当成目标；若卡住，区分视觉判断、表达能力、工具操作和规格冲突，再决定补哪里。

### T1：尺寸迁移与可复用性

同一设计新增一个更小尺寸，独立重整细节并验收，不能只调用 resize。
在测试内预留至少一个未用于调工具的角色设计，检验是否依赖首个样例。

记录首次通过情况、人工干预、生成次数、局部修复次数和失败类别。
小样本只用于定位维护价值和支持范围，不宣称泛化成功率或 Studio 普遍优于直接生成。
如需比较收益，使用相同参考、规格和生成预算，对比直接生成后处理与 Studio 工作流，
先冻结验收口径，再另行安排正式实验；本提案不执行独立 agent 实验。

### T2：受控风格与造型变体

加入第二个明确风格约定或用户授权的 Q 版比例转换，验证身份保真与允许变化能否分开。
完成后再决定是否值得建设更完整的风格包、语义区域编辑和图层能力。
不以风格名称数量作为成果。

### T3：多帧游戏角色

在已确认的单帧设计上扩展有限待机/行走，不从零独立生成每帧。
检查跨帧的服饰、色块、体积、脚底、附件点和闪烁；共享外观修改须传播或明确标出待修帧。
适合现有 rig 的角色可以使用程序化姿态，但任意位图不能自动套用 solvePose 当成已支持。
新视角、遮挡补全和非对称朝向分别声明范围；通过实际播放后才交付动画。
