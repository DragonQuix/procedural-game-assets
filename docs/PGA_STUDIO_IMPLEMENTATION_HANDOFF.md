## 0. 用户怎么使用这份文件

### 那五个文件是什么

上次回答展示的五个文件都是原项目已有文件的单独副本，不是新增功能、修改补丁，也不是需要你安装的五个组件。本次将它们逐字节与原 ZIP 对比，五个都完全一致。

| 原项目路径 | 用途 | 用户需要做什么 |
|---|---|---|
| `CONTEXT.md` | 项目术语、模块边界、坐标和交付合同的入口 | 保留原文件，让开发 agent 先读 |
| `src/core/raster.js` | 底层无抗锯齿像素绘制器 | 不要因为上次回答而覆盖、替换或单独执行 |
| `docs/recipe-guide.md` | 各类资产配方的参数和限制 | 作为开发及制作资产的参考 |
| `tools/asset-loop.mjs` | `pga-loop/2` 候选、证据和评审合同工具 | 仅在需要正式资产循环时按原协议使用，不是图像引擎启动器 |
| `docs/visual-quality.md` | 视觉质量、质量同级、证据和验收标准 | 后续开发和评测继续遵守，不把测试通过当成视觉通过 |

**不需要重新下载这五个文件，更不需要把它们覆盖回项目。只上传这五个文件不足以继续开发，因为它们不是完整代码库。**

### 新会话操作

1. 在已有仓库的编程 agent 中打开项目，或在支持文件与代码执行的新会话中上传最新完整 ZIP。
2. 附上本文件。已有仓库可将本文件放在工作区供 agent 阅读，但不要直接覆盖任何原有规则文件。
3. 复制第 13 节“首次启动提示词”。后续换会话时，提供最新项目并使用第 14 节“续接提示词”。

第 13 节刻意只要求完成 M0＋M1。完整路线覆盖后续阶段，但不要求一个会话一次性实现所有功能。每次都交付一个能运行、能验证、能继续接手的小增量。

## 2. 产品目标、范围与不做事项

### 2.1 要验证的命题

让具备基本视觉判断与结构化工具调用能力的 agent，不必手写大量像素坐标，也能：

**创建结构化起点 → 看真实渲染 → 指定一个部件及修改方向 → 比较少量候选 → 接受或回退 → 导出可继续编辑的资产。**

关键实验问题是：在相同模型和可比较的预算下，这种引擎是否比“直接写绘图代码＋看图”更稳定、更有效。

这是一项需要验证的产品假设，不是已经证明的能力。特别弱的视觉判断不能仅靠循环自动弥补。

### 2.2 首版范围

第一类资产选择：**单帧、低分辨率的机械道具或机械终端**，例如由机箱、屏幕和侧板组成的终端。使用程序化像素渲染，先做透明或完全不透明像素。

建议第一份固定样例包含：

```text
terminal.shell
terminal.screen
terminal.side_panel
terminal.base
```

第一批只做三个真实有效的操作：

| 操作 ID（建议） | 首版支持 | 不得冒充的能力 |
|---|---|---|
| `geometry.set` | 对指定部件修改已声明的宽度等有限参数 | 任意形状自动理解、任意网格变形 |
| `material.set` | 在已实现的平面/倒角金属等有限规则间切换 | 任意物体的物理光照、自然语言万能材质 |
| `ramp.set` | 为指定部件选择风格包中定义的色阶 | 全图随意重着色且声称“只改局部” |

先不要把角色动作、自动骨架、任意手绘、通用图层编辑器和云生成全部并进首版。

建议展示目标为最终 32×32 像素。当前 `assembleFrame` 默认四周增加 1px 描边边距，所以在这一配置下，内画布应是 30×30。也可选择其他尺寸，但必须明确“内画布尺寸”和“烘焙输出尺寸”，不能写 32×32 最终却无解释地得到 34×34。

### 2.3 产品边界

Studio 是现有程序化资产工具包的**创作控制层**，不是新的游戏运行时引擎。

先支持有限类别，并不把这些示例当成长期创作上限。经过有效性验证后，再增加结构组合、第二类资产、风格与动画。

首版不做：

- 重写 `PixelPainter` 或另造一套不兼容的坐标与烘焙系统。
- 任意 JavaScript 配方的自动语义反编译。
- 完整 GUI、协同编辑、账户、云端队列、复杂权限平台。
- 通用扩散模型节点编辑器、自动 LoRA 训练或默认调用收费生成服务。
- 任意 2D 风格的质量承诺。
- 将参考图裁切、嵌入或逐像素转成代码，再称为程序化原创。
- 以相似度、颜色数量、像素复杂度或一个总分替代视觉验收。

## 4. 推荐架构与代码落点

### 4.1 数据流

```text
agent / JSON CLI / optional MCP
          |
          v
     application adapter
          |
          v
document -> semantic operations -> candidate document
          |                            |
          v                            v
 shared geometry / trusted procedural renderer
          |
          v
 existing bake + BakedAsset / BakedFrame
          |
          +--> observation buffers and metadata
          +--> Canvas / gallery
          +--> PNG / atlas / manifest
```

候选和历史存储是上层编辑状态，不应加入游戏运行时帧结构。

### 4.2 初始文件组织

先少量文件跑通闭环，再按复杂度拆分，不创建一排空目录。

```text
src/studio/document.js          文档规范化、校验、稳定 ID、能力声明
src/studio/compiler.js          文档到现有烘焙数据的纯编译
src/studio/operators.js         有限的受约束文档变换（M2）
src/studio/observe.js           视图数据、对象定位、差异与诊断
src/adapters/studio-store.js    本地文档/候选/版本存储，IO 与哈希边界
bin/pga-studio.mjs              独立 JSON CLI，不破坏旧 pga.mjs

examples/studio/                自包含的文档、操作样例与 smoke 入口
tests/unit/studio-*.test.js
tests/integration/studio-cli.test.js

docs/plans/agent-studio.md      正式落地计划与阶段验收
docs/adr/<next>-agent-studio.md 架构决策（先检查下一个可用编号）
```

M3 以后可增加 `tools/mcp/` 或仓库一致的可选适配位置。不要因为加 MCP 就让浏览器烘焙核心依赖 Node SDK。

复用 `tasks/todo.md` 跟踪下一步，复用 `docs/verification.md` 记录验证，不额外建设一套平行任务平台。

### 4.3 编译桥接

MVP 可以把规范化文档编译为受信任的内存 `PropSpec`，由编译器构造绘制回调并调用 `bakeProp`；也可以通过同一底层绘制实现调用既有 `assembleFrame` / `assembleAsset`。在 ADR 中选择一种，不保留两份重复逻辑。

这里的绘制回调来自开发者维护的算子，不是执行文档中的函数文本。

建议编译输出：

```text
{
  asset: existing BakedAsset,
  sceneMap: resolved node geometry / IDs / support masks / transforms,
  diagnostics: structured diagnostics
}
```

`sceneMap` 为编辑观察侧数据，不要求改变已有对外 manifest。

几何解析只做一次，像素绘制、对象定位和元数据消费同一结果。不能分别计算画面与附件点。

如果采用新增 recipe kind，应同时检查注册表、Canvas、序列化、导出和发行消费；MVP 没有必要为了命名而引入一个全新的 kind。

## 5. 可编辑文档的最低合同

### 5.1 文档必须描述什么

下面是设计字段，不是当前仓库已经接受的输入格式。M1 将其确定成可校验的 v1。

| 字段 | 语义 |
|---|---|
| `schemaVersion` | 例如 `pga-studio/1`；未知版本拒绝，不猜测解释 |
| `id` | 资产 ID；不直接当可任意拼接的文件路径 |
| `seed` | 显式随机种子 |
| `renderProfile` | 像素渲染配置及版本 |
| `style` | 风格 ID、版本与内容指纹；不能只存一段自然语言 |
| `canvas` | 内画布宽高，以及已明确的描边/padding 策略 |
| `nodes` | 稳定 ID、父子/层序、几何类型、有限参数、材质和色阶引用 |
| `anchor` / `attachments` | 对既有坐标合同的声明或几何绑定 |
| `constraints` | 固定像素区域、结构字段、附件点等不同类别的保护规则 |
| `frames` / `clips` | 首版只需单帧；M5 后扩展，避免先写一个万能动画模式 |

持久文档只能包含可序列化数据。默认不支持函数、JS 字符串、任意模块路径、外部 URL 或自动下载执行内容。

### 5.2 校验边界

必须检查唯一 ID、引用存在、父子无环、数值有限、尺寸与内存上限、字段白名单、样式存在、操作范围与像素兼容性。

在按对象键访问时拒绝危险路径/键，例如原型链污染相关路径；文件存储不能信任节点或资产名称。

### 5.3 兼容旧配方

旧 `.mjs` 可信本地入口继续工作。不要改变旧文件语义。

旧资产可作为只读或整体节点接入；仅当实施了对应适配器时才声明可编辑字段。不能承诺任意旧函数自动变成头、背包、屏幕等语义对象。

也不要直接改变旧机器配方的种子算法，导致已有资产无意变化。新命名空间可复用相同原则并单独版本化。

## 6. 六个 agent 入口及返回合同

以下接口属于计划，不能向用户声称当前已经存在。M1 先实现 create/inspect/export 最小子集，M2 再完成编辑闭环。

| 入口 | 输入核心 | 输出核心 |
|---|---|---|
| `asset.create` | 模板/文档、显式种子、风格与约束 | assetId、初始 revision、文档摘要、预览 |
| `asset.inspect` | assetId、revision、视图/目标节点 | 实际图像、节点 ID、能力、限制、诊断 |
| `asset.edit` | baseRevision、明确操作、target、参数、保护项 | 未提交候选、影响范围、校验结果、图像 |
| `asset.explore` | 相同 baseRevision、一个操作的有限参数取值 | 基准与候选、稳定候选 ID、重复/失败说明 |
| `asset.commit` | accept 或 restore、候选/历史版本、expectedHead | 新 head、引用关系、结果哈希 |
| `asset.export` | 已提交 revision、格式与安全输出位置 | 可编辑源文档、现有资产格式和导出信息 |

`asset.inspect` 应返回当前对象支持的操作、参数范围、单位和示例，避免 agent 猜字段。

### 6.1 建议的局部探索输入

示例仅说明合同形状，最终以实施后 schema 为准：

```json
{
  "tool": "asset.explore",
  "requestId": "try-shell-width-01",
  "assetId": "terminal",
  "baseRevision": "r12",
  "target": "terminal.shell",
  "operation": "geometry.set",
  "vary": {
    "field": "widthPx",
    "values": [18, 20, 22]
  },
  "preserve": [
    {"kind": "metadata", "target": "anchor"},
    {"kind": "pixels", "target": "terminal.screen"}
  ],
  "views": ["native", "display", "target_crop"]
}
```

三个候选都从 `r12` 派生，固定种子和其他参数，不从上一个失败版本继续修改。

结果应明确关联：

```text
candidateId -> baseRevision -> operation/parameters
            -> documentHash -> renderHash
            -> constraints/diagnostics -> image references
```

没有通过保护约束的候选不得提交；不要悄悄改变 preserve 的含义。

### 6.2 无效候选和无变化

像素取整可能让不同参数得到相同图像。对渲染及元数据相同的候选去重或标注，不把重复图凑成“多样性”。

允许明确返回 `UNCHANGED`，但不得显示“已经改好”。

发现约束冲突时返回例如 `CONSTRAINT_CONFLICT`，说明冲突项与可调整参数。不能为了出图而扩大权限或静默解除锁。

### 6.3 错误返回

建议统一错误字段：

```text
code
message
target
details
retryable
suggestedNextAction
```

建议覆盖：

```text
INVALID_DOCUMENT
UNSUPPORTED_OPERATION
UNSUPPORTED_SCOPE
CONSTRAINT_CONFLICT
CLIP_ERROR
STALE_REVISION
CANDIDATE_INVALID
REQUEST_ID_CONFLICT
WORKSPACE_BUSY
UNSAFE_PATH
RESOURCE_LIMIT
```

工具错误要可诊断，但不能泄露项目外文件内容或服务密钥。

## 7. 安全编辑、版本和确定性

### 7.1 事务状态

```text
committed revision
       |
       +--> candidate A --> accepted as new revision
       +--> candidate B --> retained/discarded, never changes head
       +--> failed edit --> no new head
```

`edit` 和 `explore` 默认不改变当前正式版本。`commit` 才移动 head。

恢复旧内容时，建议创建引用旧内容的新历史节点，而不是抹去操作历史。源内容可以相同，但历史 ID 和内容哈希不是同一个概念。

### 7.2 本地存储

首版支持单工作区、单写者即可，不必实现分布式数据库。

约定：

- 工作区默认位于项目的 `work/` 中，复用已有忽略规则。
- 不可变文档快照/候选先写完整，再更新 head。
- 使用临时文件与原子替换等平台适用的方法；不要将“单次写文件”宣称为完整事务保证。
- 并发写者应锁定或拒绝，并校验 `expectedHead`；不能静默覆盖。
- 失败或进程重启后能识别未完成的临时文件，仍指向最后一个完整有效版本。
- 不自动删除用户文件；清理由明确范围与策略控制。

第一版不需要任意跨版本合并。过期候选返回 `STALE_REVISION`，让 agent 看新状态后再决定。

### 7.3 请求幂等

同一个 `requestId` 和相同请求内容重试时，返回同一结果，不重复接受候选。

相同 `requestId` 但不同内容应报冲突。重启后继续可靠使用的状态不能只存在内存。

### 7.4 三种不同的保护

**结构保护：** 某节点、字段或引用没有变化。  
**像素保护：** 某帧中规定区域的 RGBA 必须不变。  
**元数据保护：** 锚点、附件点、帧大小、剪辑引用等不变。

结构没变，不代表它在画面上没被其他部件遮挡；因此不能把结构检查当成像素检查。

局部修改依赖范围至少考虑旧/新几何、描边邻域、层序遮挡、绑定关系和已实现的明暗效果。

**禁止将“实际发生了变化的像素集合”事后定义为允许区域。**这样任何破坏都能被判合法。允许影响范围必须独立地由操作计划与依赖关系计算，再与实际差异对照。

首版图像很小，可以全量重渲染后做差分；不必先实现高复杂度脏矩形渲染。

### 7.5 确定性

相同文档、风格内容、渲染器版本与种子，应输出相同像素和元数据。

建议分别记录：

```text
documentHash  稳定序列化的内容
renderHash    RGBA 与关键元数据
toolVersion   工具/渲染器版本
styleHash     实际风格内容
```

时间戳、工作区绝对路径、随机候选 ID 不得进入确定性资产内容。

需要加密内容哈希时，在 IO 适配层使用适当实现；不要为了 `node:crypto` 打破浏览器可用的核心边界。

随机来源按稳定的资产/节点/效果命名空间分离。候选 ID、节点数组临时顺序不应成为随机来源。

动画中的静态纹理默认跨帧稳定。只有有意随时间变化的效果才将帧或时间状态纳入随机来源，避免纹理闪烁。

## 8. 观察接口与美术操作

### 8.1 最小观察集

| 视图 | 用途 |
|---|---|
| `native` | 原生尺寸检查，不靠放大掩盖缺陷 |
| `display` | 明确倍率、背景和采样的实际使用预览 |
| `target_crop` | 指定对象及邻域的局部细看 |
| `silhouette` | 按需检查轮廓与负空间 |
| `diff` | 基准/候选的实际变化和越界变化 |
| 节点编号/遮罩 | 确认目标 ID 与画面对应关系 |

M1 必须有真实 native/display PNG 和对象定位元数据。后续按需要增加其他视图，不必每次返回一张拥挤的大拼图。

放大图使用最近邻、明确倍数与坐标变换。UI 标号和编辑器遮罩只属于观察产物，不得进入最终资产。

每张图都标明对应 revision/candidate、frame、背景与尺度，避免拿错版本。

### 8.2 美术算子的落地标准

每个美术操作必须同时提供：

```text
支持的对象类型
允许参数和单位
几何/色阶/材质的实际规则
依赖及可能影响区域
限制及失败条件
前后图示例
技术测试
需要视觉判断的部分
```

`material.set` 的倒角金属首版可以使用有限的边缘带、受光侧和阴影色阶规则，不需要通用物理模拟。但不能仅随机撒几个亮点就声称完成材质理解。

色阶修改应区分共享样式引用与局部覆盖。对单个部件的改色需要局部引用/写时复制或明确全局操作，避免改动同色的全部资产。

尺寸很小时，材质细节可能不可表达；应返回已定义的简化模式或不支持，不能制造杂点凑细节。

### 8.3 风格包

首版只需要一个版本化风格定义。M4 扩展为：

```text
语义色阶
轮廓/描边规则
比例与细节尺度建议
已实现的材质规则
焦点/强调色使用规则
可组合构造件
正反例及授权来源
```

风格包不是单一模板换色器。M4 的验收必须包括不同轮廓或部件组合，而不是只导出若干颜色版本。

### 8.4 agent 接入

CLI 首先保证结构化 JSON 输入输出；日志写 stderr，不把说明文字混进 JSON 响应。现有 `pga.mjs` 的人类可读输出无需被强行改造。

MCP 作为可选薄层复用同一应用服务。返回结构化结果与真实图像内容；对不支持直接显示图像的宿主，明确本地文件/资源读取路径，并实际验证模型是否能取得图像，不能默认“返回路径＝已看图”。

MCP 官方工具规范提供 image 内容和结构化工具结果，stdio 文档要求协议输出与日志分离。实施时检查目标宿主支持的协议/SDK 版本并锁定，不照抄过期 import，不假设所有宿主行为相同。外部依据见第 16 节。

不要让 MCP、CLI 和网页适配器分别维护三套编辑逻辑。

## 9. 分阶段实施路线

阶段按验收结果推进，不在这里承诺工期。

### M0：基线、范围与架构决策

**目标：** 确认最新项目、已有能力和本轮最小边界。

工作：
- 检查根目录、Git 状态、用户未提交修改和最新规则。
- 按项目环境执行依赖安装/测试；环境无法联网时说明实际替代方法，不冒充 `npm ci`。
- 记录已存在的失败，不把它们混成新增回归。
- 在既有任务文件中添加 Studio 工作项，建立最小计划及一份必要 ADR。
- 冻结首个静态道具、尺度、保护项和操作范围。

交付：基线摘要、最小 ADR/计划、后续任务清单。

验收：指出要复用的真实函数、会新增的边界、不碰的模块。只写规划而不继续 M1，不算本轮开发任务完成。

### M1：可编辑文档 → 真实渲染 → 导出

**目标：** 在不用 agent 新写绘图函数的情况下，从结构化文档生成一个现有工具能消费的资产。

工作：
- 实现 v1 文档校验与固定样例。
- 实现单帧机械道具的纯编译桥接。
- 为节点输出定位和能力元数据。
- 实现 CLI 的 create/inspect/export 最小子集。
- 输出原生和显示预览，以及可编辑源文件与既有资产格式。
- 增加一个单命令可运行的 smoke 示例。

建议 smoke 入口名：

```text
node examples/studio/smoke.mjs --out work/studio-smoke
```

该命令是要求实施者实现的入口，**目前原仓库中不存在**。

交付：最小代码、样例文档、真实 PNG/资产输出、测试、使用方法。

验收：
- 同输入重复编译的 RGBA 与关键元数据一致。
- 不同节点有稳定可定位 ID。
- 尺寸、描边边距、锚点符合旧合同。
- 非法文档失败清楚，不静默修正。
- 旧测试无新增回归。
- 新图像确实由文档经过现有渲染核心生成，不是占位图片。
- 技术验收与视觉查看分别记录。

### M2：局部编辑、候选探索和回退（首个可用 MVP）

**目标：** 打通真正“一点一点改”的闭环。

工作：
- 实现三个有限美术操作。
- 实现未提交候选、同基准探索、候选去重。
- 实现保护项和独立计算的影响区域检查。
- 实现接受、恢复、过期版本拒绝和持久化重试。
- 提供基准/候选/接受/恢复的可见证据。
- 增加失败注入与重启恢复测试。

必做演示：

```text
创建终端
→ 查看节点和原图
→ 只探索机箱宽度的三个版本
→ 检查屏幕像素与锚点保护
→ 接受其中一个
→ 尝试不符合保护条件的修改，明确拒绝
→ 恢复初始版本
→ 确认恢复后像素和元数据哈希一致
→ 导出
```

验收：不是“有六个 API 名字”，而是上述流程能真实运行，并能证明错误候选没有污染 head。

### M3：真实 agent 接入与小规模对照评测

**目标：** 验证工具是否降低能力要求，再决定扩张方向。

工作：
- 在可用宿主中实际跑视觉 agent 流程；先用 CLI＋读图也可。
- 需要 MCP 时才添加薄适配；核对官方版本与宿主行为。
- 运行第 10 节的预先定义试点任务。
- 记录失败类型：不认识目标、不会选参数、看不到图、判断错误、参数空间不足、工具保护失效。
- 优先修复重复出现且能改善工具的原因，不为单次演示无限美化。

验收：
- 至少一个真实宿主能接收并使用真实渲染图像。
- 有可复查的调用与候选轨迹。
- 能区分工具改进与更强模型/更多计算/更精美模板的作用。
- 未拿到独立评测资源时，只宣称“接口可用/技术试验完成”，不宣称帮助弱 agent 已获证实。

**阶段决策：** 若候选始终难以选好，先改观察和操作设计；若模板本身限制表现，进入 M4；若没有可用收益，收窄范围而不是用更多 API 掩盖问题。

### M4：风格与构造能力

**目标：** 从一个演示模板变成有适度创作空间的资产工具。

工作：
- 风格版本、局部覆盖、参考与许可。
- 增加第二种结构明显不同的静态资产或构造组合。
- 增加真正支持体积/材质/细节概括的有限操作。
- 用留出的新组合任务检验，不把全部测试写成已知模板参数。

验收：共享风格但轮廓、构造或功能标识明显不同的资产能够成立；不是单纯换色。记录哪些表现仍超出能力。

### M5：角色、跨帧与资产族

**目标：** 将修改一致传播到明确支持的角色和动作。

工作：
- 选择一个已有角色及其现有待机/移动剪辑，复用 `solvePose`。
- 区分资产级共享字段、节点字段与帧覆盖。
- 头部、装备或材质调整正确影响所需帧。
- 自动报告所有受影响帧和附件点。
- 对未适配的特殊姿态明确返回不支持，不假装覆盖。
- 生成实际播放材料，而不只做帧拼图。
- 通过现有 Canvas/导出路径验证。

验收：同一修改在约定动作中保持身份、接地、附件关系与材质一致。动画的视觉验收必须实际观看播放。

M5 不要求一下支持原项目全部姿态、任意骨架或任意生物。

### M6：发行、文档与现有流程接入

**目标：** 让其他 agent 在干净项目里可靠使用。

工作：
- 将稳定入口、参数与错误例子加入开发源文档。
- 检查 `tools/release.mjs` 的载荷清单：`src`/`bin` 已整体携带，但新的 `examples/studio`、文档和可能的 MCP 目录不会因此自动完整进入载荷。
- 按已批准的发布范围调整白名单和依赖携带。
- 使用发行脚本生成派生载荷，不手改其内容或哈希清单。
- 验证干净目录初始化、文档相对链接、自包含依赖和实际运行。
- 准确区分普通版/循环版发布范围；不能因根版本变化自动推断两种入口都应该升级。
- 不自动修改任何用户级技能安装、共享项目或宿主配置。

现有发行命令应在实际阶段核对后使用：

```text
node tools/release.mjs --check
node tools/release.mjs --skill procedural-game-assets-loop --check
```

无 `--check` 会重建相应载荷，只在明确的发行任务中运行。

严格资产循环接入：
- 内层 Studio 创作候选可以快速试错，不冒充正式冻结候选。
- 需要严格交付时，再将接受版本通过现有流程冻结并接受独立评审。
- 不把自身自审自动写成独立 WOW，不复用已经变化资产的旧裁决。

M6 可以在 M3 后对有限范围发布 alpha，不必等所有动画能力完成，但必须清楚标明实际支持范围。

## 10. 评测设计：证明收益，而不是展示漂亮截图

### 10.1 分组

| 组别 | 工具配置 | 回答的问题 |
|---|---|---|
| A | 同一个 agent，当前写代码＋看图 | 现状基线 |
| B | 同一个 agent，底层绘图操作接口 | 只减少代码组织负担有多大作用 |
| C | 同一个 agent，语义节点与美术操作，不做候选搜索 | 中层操作的增益 |
| D | 同一个 agent，语义操作＋少量候选探索 | 搜索与比较的额外增益 |

可另设较强 agent 使用 A 的参照，但不可将评价者/生成器更强的收益算成工具收益。

### 10.2 首轮试点

建议预先选定 12 个小任务，每个多次重复，例如 3 次。该数量只适合筛查问题，不足以证明对所有模型普遍有效。

初始任务覆盖：
- 有明确结构要求的静态新建。
- 比例、层级或材质的局部修复。
- 带像素/附件点保护的编辑。

M4 后增加未见构造组合，M5 后增加跨帧一致性。不要在 M3 就虚构尚未实现的动画任务结果。

统一种子集合、原生和显示条件、风格资料与质量要求。基线也应得到可比较的素材与规则信息，避免把模板优势混成接口优势。

固定每组可比较的资源边界并记录全部实际消耗。这个实验预算不改变严格资产循环默认合同。

### 10.3 记录什么

| 维度 | 记录方式 |
|---|---|
| 需求完成度 | 预先声明要求的满足/未满足/未验证 |
| 视觉质量 | 使用现有标准；盲比允许 A、B、无明显差异、都未达标 |
| 局部安全 | 应保护区域/字段是否被误改，错误是否被阻断 |
| 效率 | 总调用、视觉观察、候选数、返修、端到端用时 |
| 成本 | 全部模型调用、图片输入、候选渲染与额外评价成本 |
| 稳定性 | 同类任务多次运行表现，失败类型分布 |

不要只报告最好的一张，失败、拒绝和重复候选也计入成本。

实际模型和收费价格在实施评测时核对；本方案不预填可能过期的价格或模型排名。

### 10.4 视觉结论

遵守 `docs/visual-quality.md`。原生/使用尺度、整体美学、设计要求和必要帧覆盖分开记录。

技术 `PASS` 不等于视觉 `PASS`。缺少实际图像观察或播放时记 `UNVERIFIED`。没有参考的维度按独立要求判断，不伪造“与标杆同级”。

评测前写明要支持的结论和可接受的成本变化，结果出来后不能更换任务或较低标杆来宣布成功。先报告限定模型、限定样例内的证据，再扩大实验。

没有其他模型或人工评价资源时，交付评测脚本/任务与已运行的技术部分，标记未执行部分。不虚构实验结果，不未经许可调用收费 API。

## 11. 关键测试矩阵与完成定义

| 测试 | 最低要求 |
|---|---|
| 文档校验 | 重复 ID、未知样式、非法尺寸、非有限数、坏引用/环、危险路径拒绝 |
| 确定性 | 同输入、同版本、同种子得到同 RGBA 与元数据 |
| 坐标/边距 | 内画布、最终帧、裁切图坐标与 anchor/attachments 可正确映射 |
| 局部编辑 | 允许区域外无意变化可被发现并阻止 |
| 共享样式 | 局部改色不无意修改其他节点或资产 |
| 事务 | 失败编辑和部分写入不改变有效 head |
| 并发/过期 | 同时写入不静默覆盖；过期基准拒绝 |
| 重试 | 相同 requestId 幂等，不同请求冒用 ID 报错 |
| 恢复 | 恢复后像素/元数据精确一致，历史不被抹除 |
| 观察一致性 | 图片、节点 ID、revision、元数据一一对应 |
| CLI | JSON 可解析，错误码与日志渠道清楚 |
| 兼容 | 既有配方、测试、Canvas 与导出无新增回归 |
| 动画（M5） | 修改覆盖所有已声明帧，实际播放检查另行记录 |
| 发行（M6） | 干净携带、依赖、引用与载荷校验可用 |

每阶段“完成”至少包括：

**实际代码或明确可复用成果、可执行入口、必要测试、可观察证据、真实限制、更新的下一步。**

不允许以接口占位、空目录、概念图、打印成功消息、合成评审记录或文档篇幅替代功能。

也不要为了填满测试表而维护无复用价值的外部演示工程；按 `AGENTS.md` 优先解决会改进工具本身的缺陷。

## 12. 风险与处置

| 风险 | 处置 |
|---|---|
| 工具太底层，agent 仍需自己当像素画师 | 优先实现有限但完整的美术操作，而不只暴露画点/画线 |
| 工具太抽象，修改不可预测 | 参数有范围、单位、前后例子、依赖和失败定义 |
| 候选越多成本越高但没有收益 | 小批探索、去重、记录成本；通过对照实验决定数量 |
| 选择能力弱，越改越差 | 保留基准、允许平局/不接受；改观察或收窄任务，不自动接受“最后一张” |
| 一直微调却无法改变坏轮廓 | M4 增加有限结构分支，不让系统只会增加细节 |
| 风格包过拟合模板 | 使用结构不同的资产与留出组合测试 |
| 旧配方被改坏 | 新增适配层、旧种子行为不变、旧测试和真实像素回归 |
| 架构过重 | M1/M2 少量文件和本地单写者；不提前建设云平台 |
| 工具看起来会审美，实际只是数值门禁 | 技术和视觉结论分开，保留 UNVERIFIED |
| 不同宿主拿不到图 | 验证真实图像内容到达模型；不要只检查返回的文件路径 |
| 生成后端掩盖引擎贡献 | 纯程序化与模型辅助分组，单独计算来源/成本 |
| 上下文丢失反复规划 | 每轮更新同一任务入口和下一项可执行任务，不重开一套计划 |

## 13. 首次启动提示词（复制给新会话 agent）

```text
你正在继续开发 procedural-game-assets。请使用当前工作区的最新项目，阅读我附上的《PGA_STUDIO_IMPLEMENTATION_HANDOFF.md》，直接实施其中 M0＋M1，不要只重新输出方案，也不要一次性实现 M2–M6。

背景与目标：
现有工具包已有确定性像素绘制、配方、姿态、烘焙、Canvas 接入、导出、画廊和质量评审。现在新增的是 agent 使用的创作控制层，暂称 PGA Studio。目标是让视觉 agent 通过结构化部件和受约束操作逐步制作资产，而不必每次手写大量绘图代码。
首版选择单帧机械道具/终端，先跑通“可编辑文档 → 现有烘焙核心 → 真实预览 → 既有资产导出”。候选编辑、搜索和回退留给 M2。
```
